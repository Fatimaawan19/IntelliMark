1.1 PURPOSE & OBJECTIVES
────────────────────────────────────────────────────────────────────────────────

The Plagiarism Detection System identifies:
✓ Student-to-student copying (Internal Plagiarism)
✓ AI-generated content usage (External Plagiarism)
✓ Online resource reuse (via ZeroGPT API)

Key Features:
- Dual-mode detection: INTERNAL (FAISS similarity) + EXTERNAL (AI detection)
- Intelligent mode switching (external-only when single submission)
- Graceful API fallback (works without ZeroGPT if API unavailable)
- Persistent scoring across teacher re-logins
- Real-time terminal logging for monitoring


1.2 FUNCTIONALITY
────────────────────────────────────────────────────────────────────────────────

Core Features:
1. Internal Plagiarism Detection
   - Compare student answers with other students in same assessment
   - FAISS vector similarity search (faiss_submissions_index)
   - Returns top 5 similar submissions with similarity percentages

2. External Plagiarism Detection
   - Detect AI-generated content via ZeroGPT API
   - Returns AI score (0-100%) and GPT-generated flag
   - Graceful fallback to 0% if API fails

3. Combined Risk Scoring
   - Formula: overallScore = (internalScore × 0.6) + (aiScore × 0.4)
   - Risk Level Classification:
     * Low (0-29%)
     * Medium (30-59%)
     * High (60-100%)

4. Detection Mode Selection
   - "both_internal_external": Multiple submissions (normal mode)
   - "external_only": Single submission in assessment (no internal comparison possible)
   - Automatic mode detection based on submission count


1.3 STEP-BY-STEP IMPLEMENTATION
────────────────────────────────────────────────────────────────────────────────

STEP 1: Teacher Initiates Plagiarism Check
   └─ POST /api/plagiarism/check/:submissionId
   └─ Optional: ?refresh=true to force recalculation

STEP 2: Backend Detection Mode Selection
   Code:
   ```javascript
   const otherSubmissionCount = await Submission.countDocuments({
     assessmentId: sub.assessmentId,
     _id: { $ne: submissionId },
     assessmentType: "assignment"
   });

   const detectionMode = otherSubmissionCount === 0 ? "external_only" : "both_internal_external";
   ```

STEP 3: Internal Plagiarism Check (if mode = "both_internal_external")
   - Extract student's answer text from SubmissionRaw
   - Query FAISS submissions index with answer text
   - Exclude: same student + different assessments
   - Get top 15 matches, filter to top 5 by similarity
   - internalScore = highest match similarity × 100

   Code:
   ```javascript
   if (detectionMode === "both_internal_external") {
     const internalMatches = await queryInternalSimilarity(
       text,
       submission.studentId,
       submission.assessmentId,
       topK: 15
     );
     internalScore = Math.max(...internalMatches.map(m => m.similarity)) * 100;
   }
   ```

STEP 4: External Plagiarism Check (AI Detection)
   - Send student answer to ZeroGPT API
   - API analyzes patterns typical of GPT-generated content
   - Returns: aiScore (0-100%) + isGptGenerated flag + feedback
   - If API fails (401/403/timeout): fallback to aiScore = 0%

   Code:
   ```javascript
   const aiResult = await detectAIContent(text);
   // Returns: {aiScore: 0-100, isGptGenerated: bool, feedback: string}
   ```

STEP 5: Calculate Combined Score
   ```javascript
   const overallScore = Math.round(
     (internalScore × 0.6) + (aiScore × 0.4)
   );

   const riskLevel =
     overallScore >= 60 ? "high" :
     overallScore >= 30 ? "medium" :
     "low";
   ```

STEP 6: Store Results (Two Locations for Sync)
   Location 1 - PlagiarismReport Collection:
   ```
   {
     submissionId, assessmentId, studentId,
     internalScore, aiScore, overallScore,
     topMatches: [{studentName, similarity, ...}],
     riskLevel, checkedAt
   }
   ```

   Location 2 - Submission Model (sync copy):
   ```
   {
     plagiarismBestMatchPercent: internalScore,
     plagiarismAiScore: aiScore,
     plagiarismReport: {...full snapshot},
     plagiarismCheckedAt: Date
   }
   ```

STEP 7: Frontend Display
   - ViewReport.tsx shows:
     * "Student submission match: X%"
     * "AI-generated content: Y%"
     * Colored badges (Red >70%, Amber >0%, Gray 0%)

1.7 AI/ML LOGIC
────────────────────────────────────────────────────────────────────────────────

Internal Plagiarism (FAISS Vector Similarity):
1. Each student answer is converted to embedding vector
   - Uses: sentence-transformers/all-MiniLM-L6-v2 (384-dimensional vectors)
   - Model is 22.4MB, runs on CPU

2. Embeddings stored in FAISS index (faiss_submissions_index/)
   - Index type: Flat (exact nearest neighbor search)
   - Similarity metric: L2 distance → converted to cosine similarity

3. Query process:
   - Convert new answer to embedding
   - Find top-K nearest neighbors in index
   - Similarity score = 1 - (L2_distance / max_distance)
   - Range: 0-1 → converted to 0-100%

External Plagiarism (ZeroGPT API):
1. ZeroGPT analyzes text for AI patterns:
   - Sentence structure patterns typical of GPT
   - Vocabulary complexity matching GPT outputs
   - Statistical language model analysis

2. Returns:
   - fake_percentage: 0-100% (confidence AI-generated)
   - is_gpt_generated: boolean flag
   - additional_feedback: confidence explanation

3. Score weighting (why 60/40?):
   - Internal (60%): Direct plagiarism from other students (more severe)
   - External (40%): AI usage (concerning but different violation)
   - Reasoning: Student-to-student copying is more critical to detect


1.8 CHALLENGES & WHY THIS APPROACH
────────────────────────────────────────────────────────────────────────────────

Challenge 1: ZeroGPT API Reliability
Problem: API key expiration, credit exhaustion, timeouts (401/403/500 errors)
Why this approach:
- Graceful fallback to aiScore = 0% (system doesn't crash)
- Terminal logging for debugging
- User can add valid API key anytime and re-run
Solution implemented:
```javascript
async function detectAIContent(text) {
  try {
    const {data} = await axios.post(ZEROGPT_API_URL, {input_text: text}, {timeout: 20000});
    return {aiScore: data.data.fake_percentage, isGptGenerated: data.data.is_gpt_generated};
  } catch (err) {
    console.warn("[PLAGIARISM] ZeroGPT unavailable:", err.message);
    return {aiScore: 0, isGptGenerated: false, error: err.message};
  }
}
```

Challenge 2: Penalty Applied Even with No Matches
Problem: Old code applied 43% penalty even if 0 students matched
Why this approach:
- Only apply penalty if actual matches exist: matches.length > 0
- Prevents false positives
Solution:
```javascript
const penaltyPercent = matches.length > 0 ? computePenaltyPercent(best) : 0;
```

Challenge 3: Single Submission Assessments
Problem: Can't do internal plagiarism check if only 1 student submitted
Why this approach:
- Detect: Count submissions in assessment
- If count === 0: Skip FAISS query, only run external check
- detectionMode = "external_only"
Solution: Automatically switches modes without requiring teacher action

Challenge 4: Score Persistence Across Sessions
Problem: Plagiarism scores change on re-login (caching issue)
Why this approach:
- Cache results immediately after first check
- Don't recalculate unless ?refresh=true
- Store in TWO locations (PlagiarismReport + Submission) for redundancy
- Teacher can explicitly refresh with "refresh=true" parameter

Challenge 5: Question Text Contamination
Problem: FAISS similarity includes question text, not just answers
Why this approach:
- Extract only student's written answer (not question)
- Query FAISS with answer-only text
- Prevents false positives from identical questions


1.9 INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q1: "How does your plagiarism detection system work?"
A: "We use a dual-mode system:
   1. INTERNAL: FAISS vector similarity to find similar student answers (60% weight)
   2. EXTERNAL: ZeroGPT API to detect AI-generated content (40% weight)

   The system intelligently detects if there's only one submission and switches to
   external-only mode. Results are stored in both PlagiarismReport collection and
   Submission model for cross-login persistence. If ZeroGPT API fails, we gracefully
   fallback to 0% AI score without crashing the system."

Q2: "Why did you use 60% weight for internal and 40% for external?"
A: "Student-to-student plagiarism is more severe academically than AI usage.
   Direct copying (internal) shows academic dishonesty, while AI usage is a policy
   violation. The 60/40 split prioritizes catching direct copying while still
   flagging AI usage. This is also industry standard for plagiarism detection systems."

Q3: "What happens if ZeroGPT API is down?"
A: "The system gracefully degrades:
   - Internal plagiarism check continues normally
   - aiScore is set to 0%
   - Error is logged to console with [PLAGIARISM] prefix
   - System doesn't crash
   - Teacher can provide valid API key and re-run with ?refresh=true
   - Results are deterministic: same submission always returns same score (cached)"

Q4: "How do you ensure scores don't change on teacher re-login?"
A: "We cache results immediately after first check using PlagiarismReport.findOneAndUpdate
   with {upsert: true}. We don't recalculate unless teacher explicitly requests
   refresh=true. We also store a snapshot in Submission model as backup."

Q5: "How do you handle the single submission case?"
A: "If a teacher creates an assessment and only one student submits:
   1. Count other submissions: countDocuments({assessmentId, _id != current})
   2. If count === 0: detectionMode = 'external_only'
   3. Skip FAISS query entirely (no other students to compare with)
   4. Only run ZeroGPT API for AI detection
   5. Return with detectionMode in response for UI indication"

Q6: "Why store results in two database locations?"
A: "Data consistency and redundancy:
   - PlagiarismReport: Full detailed report (for admin view)
   - Submission.plagiarismBestMatchPercent: Quick access (for student report)
   - Prevents sync issues if one collection becomes corrupted
   - Faster queries (don't need JOIN operations)"

Q7: "What's your approach to false positives?"
A: "Several safeguards:
   1. Only compare answers in same assessment (filter by assessmentId)
   2. Exclude question text from similarity (extract answers only)
   3. Only penalize if actual matches exist (matches.length > 0)
   4. Use soft threshold for risk levels (not binary detection)
   5. Show top 5 matches to teacher for human verification"

Q8: "How do you extract just the answer without question text?"
A: "We use extractAnswersOnly() function that:
   1. Identifies question boundaries in student submission
   2. Removes question text that student didn't write
   3. Sends only student's written content to FAISS
   4. This prevents false positives from identical questions"

2.1 PURPOSE & OBJECTIVES
────────────────────────────────────────────────────────────────────────────────

The AutoMark module automatically grades student submissions using:
✓ Large Language Models (LLMs) for intelligent evaluation
✓ Retrieval-Augmented Generation (RAG) for context
✓ Sample answer patterns for reference
✓ Rubric-based scoring criteria

Key Features:
- Multi-question per-question grading
- Cloud (Groq) + local (Ollama) LLM support with fallback
- RAG-based context retrieval (FAISS indices)
- Sample answer reference for pattern matching
- Confidence scoring and teacher review flags
- Batch processing for multiple submissions
- Re-AutoMark capability (remark without re-embedding)


2.2 FUNCTIONALITY
────────────────────────────────────────────────────────────────────────────────

Core Features:
1. Smart Chunk Retrieval (RAG)
   - Query FAISS indices for relevant context:
     * Student's own past answers (faiss_submissions_index)
     * Sample answer patterns (faiss_assessment_reference_index)
     * Course learning materials (faiss_index)
   - Top-K retrieval (k=8-15) for rich context

2. LLM-Based Grading
   - Send question + student answer + context + rubric to LLM
   - LLM returns:
     * Per-question score (0-max points)
     * Detailed feedback explaining the score
     * Identified mistakes with explanations
     * Suggestions for improvement
     * Confidence level (0-100%)

3. Batch Processing
   - Supports automarking all submissions in assessment
   - Queue-based processing (one submission at a time)
   - Real-time progress updates via job polling
   - Graceful error handling and retry logic

4. Re-AutoMark Capability
   - Re-grade without re-embedding (crucial for performance)
   - Queries existing FAISS chunks, skips ingestion
   - Useful when:
     * Teacher updates rubric
     * Teacher wants different LLM perspective
     * Previous grading had errors

2.7 AI/ML LOGIC
────────────────────────────────────────────────────────────────────────────────

Prompt Engineering Strategy:
```
1. ROLE DEFINITION
   "You are an expert teacher grading student submissions"
   → Sets context for LLM to think pedagogically

2. RUBRIC INTEGRATION
   Provide exact scoring criteria:
   "Q1: 10 points max
    - 8-10: Correct answer with clear reasoning
    - 5-7: Correct answer but incomplete explanation
    - 2-4: Partially correct approach
    - 0-1: Incorrect approach"
   → LLM aligns scoring with teacher expectations

3. CONTEXT INJECTION (RAG)
   Include:
   - Sample answer chunks (what good looks like)
   - Similar student answers (realistic examples)
   - Course materials (reference material)
   → Reduces hallucination, improves consistency

4. STRUCTURED OUTPUT
   Request JSON format:
   {
     score: Number,
     feedback: String,
     mistakes: Array,
     confidence: Number
   }
   → Easy to parse, prevents ambiguity

5. EXPLICIT INSTRUCTIONS
   "Identify specifically:
    - What the student got right
    - What mistakes exist
    - Why the answer is incomplete"
   → More detailed, actionable feedback
```

RAG Strategy:
```
Three-tiered context retrieval:

Tier 1: Student's Past Answers
├─ FAISS submissions index
├─ Retrieve: Top 8 chunks from student's own previous submissions
├─ Purpose: Show what level student normally works at
└─ Weight: 30% similarity relevance

Tier 2: Sample Answer Reference
├─ FAISS assessment reference index
├─ Retrieve: Top 8 chunks from teacher's sample answer
├─ Purpose: Show ideal answer structure and content
└─ Weight: 50% similarity relevance

Tier 3: Course Materials
├─ FAISS course index
├─ Retrieve: Top 8 chunks from syllabus/lectures/resources
├─ Purpose: Provide factual reference material
└─ Weight: 20% similarity relevance

Total context size: ~2000-3000 tokens
Ensures LLM has sufficient context without token overflow
```

LLM Model Selection Logic:
```
IF Groq API available AND GROQ_API_KEY valid:
  ├─ Use: llama-3.1-8b-instant
  ├─ Speed: ~2 seconds/question
  ├─ Cost: Free tier or paid
  └─ Quality: Excellent at reasoning
ELSE IF Ollama running locally:
  ├─ Use: qwen2.5:7b or phi3:mini
  ├─ Speed: ~15 seconds/question
  ├─ Cost: $0 (local)
  └─ Quality: Good, offline capable
ELSE:
  └─ Return error: "No LLM available"

Confidence Scoring:
- Range: 0-100%
- Factors:
  * LLM's stated confidence
  * Length of feedback (more detailed = higher confidence)
  * Match with rubric criteria
  * Context availability (better context = higher confidence)
```


2.8 CHALLENGES & WHY THIS APPROACH
────────────────────────────────────────────────────────────────────────────────

Challenge 1: Re-AutoMark Stuck on "Running"
Problem: Second automark would hang indefinitely
Root cause: Re-running prepareOneSubmission(force: true) which:
  - Re-extracts all text
  - Re-chunks everything
  - Re-generates embeddings (SLOW, 5-10 minutes)
  - Often timed out

Why this approach:
```javascript
// Old (broken):
startAssessmentRemarkBatch() {
  for (submission of submissions) {
    prepareOneSubmission(sub, {force: true}); // RE-EMBEDS - SLOW!
    grade(sub);
  }
}

// New (fixed):
runMarkingBatch(job, submissions, assessment, questions, {isRemark: true}) {
  if (isRemark) {
    // Skip extraction entirely!
    // FAISS chunks already exist from first automark
    retrieveContext(sub);  // Just query, don't rebuild
    grade(sub);
  } else {
    prepareOneSubmission(sub, {force: false});  // First run only
    retrieveContext(sub);
    grade(sub);
  }
}
```

Solution: Shared runMarkingBatch() function that:
- Passes isRemark flag
- If isRemark=true: Skip extraction, reuse chunks
- If isRemark=false: Extract once, then query
- Result: 5-10x faster re-automark, no hanging

Challenge 2: FAISS Index Corruption/Missing Data
Problem: Chunks not extracted properly, or FAISS index empty
Symptoms:
- sampleAnswerExtracted = false (but file uploaded)
- relevantCourseMaterialChunksExtracted = false (but materials exist)

Why this approach:
```javascript
// Probing mechanism - check if chunks exist
if (!sampleAnswerExtracted) {
  const probe = await queryAssessmentReferenceChunks(probeText);
  if (probe.length > 0) {
    // Chunks exist! Update flag
    sampleAnswerExtracted = true;
  }
}

// Fix script for bulk repair:
// node scripts/fix-failed-automark-extractions.js --dry-run
// node scripts/fix-failed-automark-extractions.js
```

Solution: Auto-probing + fix script:
- Probes check if chunks actually exist
- Fix script can recover failed flags
- Teachers run fix once, extractions work forever

Challenge 3: LLM Hallucination & Inconsistency
Problem: Same question graded differently on different runs
Why this approach:
- Low temperature (0.3): More deterministic
- Explicit rubric: Guides scoring
- RAG context: Reduces creativity/hallucination
- Sample answers: Shows expected format
- Confidence scoring: Flags uncertain gradings
- Teacher review flag: Marks low-confidence answers

Challenge 4: Token Overflow (Prompt Too Long)
Problem: Too much context = exceeds LLM token limit (4K for Groq, 8K for Ollama)
Why this approach:
- Cap context: Top 8 chunks per source (max 3 sources)
- Semantic relevance: Retrieve most similar chunks only
- Truncate long chunks: Max 300 tokens each
- Total prompt: ~2000-3000 tokens (safe for all LLMs)

Challenge 5: Groq API Timeout/Failure
Problem: Groq unavailable, teacher can't grade
Why this approach:
```javascript
try {
  return await callGroqAPI(prompt);
} catch (err) {
  console.warn(`[AUTOMARK] Groq failed, falling back to Ollama`);
  return await callOllamaAPI(prompt);
}
```

Solution: Automatic fallback:
- Try Groq first (fast cloud)
- If fails: Fall back to Ollama (slow local)
- If both fail: Return error but don't crash
- Teacher can retry or mark manually


2.9 INTERVIEW QUESTIONS & ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q1: "How does your AutoMark system grade student submissions?"
A: "We use a retrieval-augmented generation (RAG) approach with LLMs:

1. When a teacher clicks AutoMark, we first extract all student submissions
   into FAISS indices for semantic search.

2. For each question, we retrieve three types of context:
   - Similar student answers (from FAISS submissions index)
   - Sample answer chunks (from FAISS reference index)
   - Course material context (from FAISS course materials index)

3. We combine all this context into a detailed prompt and send it to an LLM.
   We use Groq (cloud, fast) by default, with Ollama (local) as fallback.

4. The LLM grades the answer based on the rubric and context, returning:
   - Score and feedback per question
   - Identified mistakes with explanations
   - Confidence level and teacher review flag

Q2: "Why do you use both Groq and Ollama?"
A: "Different trade-offs:
   - Groq: Cloud-based, very fast (~2 seconds), needs internet and API key
   - Ollama: Local, works offline, free, but slower (~15 seconds)

   We use Groq as primary for speed, Ollama as fallback for reliability.
   If Groq API is down or user doesn't have key, they can still grade using
   Ollama. This ensures the system never completely breaks due to external dependencies."

Q3: "What is RAG and why do you use it?"
A: "RAG = Retrieval-Augmented Generation. Instead of relying only on the LLM's
   training data, we retrieve relevant context from our FAISS indices and
   include it in the prompt.

   Why:
   - Reduces hallucination (LLM not making up facts)
   - Grounds answers in actual course materials
   - Shows example answers (sample answer)
   - Shows realistic student work (similar answers)
   - More consistent grading across submissions
   - Scores align with teacher's expectations (via rubric + context)"

Q4: "How do you prevent re-AutoMark from hanging?"
A: "This was a major bug! The problem was that every re-AutoMark would
   re-extract and re-embed all submissions (5-10 minutes per submission).

   The fix was to refactor into a shared runMarkingBatch() function that
   accepts an isRemark flag:

   - First AutoMark (isRemark=false): Extract → Query → Grade
   - Re-AutoMark (isRemark=true): Skip extraction → Query → Grade

   The key insight: FAISS indices are persistent on disk. Once chunks are
   indexed, they stay there. We don't need to re-embed; we just query the
   existing index. This makes re-AutoMark 5-10x faster and never hangs."

Q5: "What happens if extraction flags are false?"
A: "If sampleAnswerExtracted or relevantCourseMaterialChunksExtracted are false,
   the system still works but with reduced context quality.

   Our approach:
   1. Auto-probe: Check if chunks actually exist in FAISS
   2. If they exist: Update flag to true (recovery)
   3. If they don't: Flag stays false, indicate to teacher

   We also built a fix script:
   $ node scripts/fix-failed-automark-extractions.js --dry-run

   This finds all jobs with false flags and tries to re-extract them.
   Teachers can run this once to fix all broken flags."

Q6: "How do you ensure consistent grading?"
A: "Several strategies:
   1. Low temperature (0.3): Makes LLM more deterministic
   2. Explicit rubric: Guides scoring criteria
   3. RAG context: Shows reference answers
   4. Confidence scoring: Flags uncertain answers (0-100%)
   5. Teacher review flag: Marks answers needing human review

   Even with these, there can be variation between runs. That's why we
   cache results: once graded, we don't re-grade unless teacher explicitly
   asks for it with the Re-AutoMark button."

Q7: "How do you handle LLM failures?"
A: "Multiple fallback mechanisms:

   1. Groq → Ollama: If Groq fails, try local Ollama
   2. Partial success: If one question fails, others still grade
   3. Error logging: Every failure is logged with [AUTOMARK] prefix
   4. Teacher intervention: If grading fails, teacher marks manually
   5. Re-AutoMark: Can retry grading with different LLM

   The system never crashes; it gracefully degrades."

Q8: "What's the difference between first AutoMark and Re-AutoMark?"
A: "First AutoMark:
   1. Extract submissions (OCR, PDF parsing)
   2. Chunk and embed text
   3. Index to FAISS (slow, 5-10 min)
   4. Query FAISS for context
   5. Grade with LLM

   Re-AutoMark:
   1. Skip extraction (FAISS already has it)
   2. Skip embedding (indices are built)
   3. Skip indexing (chunks persistent)
   4. Query FAISS for context (instant)
   5. Grade with LLM

   Result: Re-AutoMark is 5-10x faster, never hangs, no re-embedding needed.
   Useful when teacher wants to change rubric or get second opinion from LLM."

4.3 STEP-BY-STEP IMPLEMENTATION
────────────────────────────────────────────────────────────────────────────────

Python Script: backend/rag_marking/ingest_materials_to_faiss.py

```
STEP 1: Discover Files
  └─ Scan backend/uploads/ for course materials
  └─ Filter by course ID if specified

STEP 2: Extract Text
  ├─ For PDF:
  │   ├─ Use PyMuPDF: extract_text()
  │   ├─ If text quality low: Use pytesseract OCR
  │   └─ Preserve page numbers in metadata
  │
  ├─ For DOCX:
  │   ├─ Use python-docx: iterate paragraphs
  │   └─ Extract tables separately
  │
  └─ For TXT:
      └─ Direct file read

STEP 3: Semantic Chunking
  ├─ Split on sentence boundaries (using NLTK)
  ├─ Group sentences until chunk size ≤ 512 tokens
  ├─ Create overlapping chunks (50-token overlap)
  └─ Store metadata: {source_file, page, topic, chunk_index}

STEP 4: Generate Embeddings
  ├─ Initialize: sentence-transformers.SentenceTransformer('all-MiniLM-L6-v2')
  ├─ Encode chunks: model.encode(chunks, batch_size=32)
  └─ Output: List of 384-dimensional vectors

STEP 5: Build FAISS Index
  ├─ Initialize: faiss.IndexFlatL2(384)  // L2 distance
  ├─ Add vectors: index.add(embeddings)
  ├─ Save index: index.write(faiss_index/index.faiss)
  └─ Save metadata: pickle.dump(metadata, faiss_index/index.pkl)

STEP 6: Store Mapping
  └─ Store chunk_id → (source_file, page, topic) in JSON
```

Usage Commands:
```bash
# Ingest all materials for a course
python ingest_materials_to_faiss.py --course-id 6a03ea92607a94991f0252f0

# Ingest with test run (5 chunks max)
python ingest_materials_to_faiss.py --course-id 6a03ea92607a94991f0252f0 --limit 5

# Ingest all courses
python ingest_materials_to_faiss.py
```

Query Interface:

```python
# Load index at startup
def load_faiss_index(course_id):
    index = faiss.read_index(f"faiss_index/index.faiss")
    metadata = pickle.load(open(f"faiss_index/index.pkl", "rb"))
    return index, metadata

# Query for similar chunks
def query_course_materials(query_text, course_id, top_k=8):
    index, metadata = load_faiss_index(course_id)
    query_embedding = encoder.encode([query_text])[0]  # 384-dim vector
    distances, indices = index.search(np.array([query_embedding]), k=top_k)

    results = []
    for idx in indices[0]:
        chunk = metadata[idx]
        results.append({
            'text': chunk['text'],
            'source': chunk['source_file'],
            'page': chunk['page'],
            'similarity': 1 - (distances[idx] / max_distance)  // convert to similarity
        })
    return results
```

- Adaptive PSM (Page Segmentation Mode) selection
- Fallback to PDF text extraction if available
- Confidence scoring


5.2 STEP-BY-STEP IMPLEMENTATION
────────────────────────────────────────────────────────────────────────────────

Python Script: backend/rag_marking/opencv_digitize.py

```
STEP 1: Load Image
  └─ cv2.imread(image_path)

STEP 2: Convert to Grayscale
  └─ cv2.cvtColor(image, cv2.COLOR_BGR2GRAY)
  └─ Reduces computational load

STEP 3: Upscale (if low resolution)
  ├─ Check image height
  ├─ If height < 2000: Upscale using INTER_CUBIC
  ├─ cv2.resize(image, (width*2, height*2), interpolation=cv2.INTER_CUBIC)
  └─ Improves OCR accuracy

STEP 4: Denoise
  └─ cv2.fastNlMeansDenoising(image, h=10)
  └─ Removes noise, preserves edges

STEP 5: Adaptive Thresholding
  └─ cv2.adaptiveThreshold(image, 255, cv2.ADAPTIVE_THRESH_GAUSSIAN_C, cv2.THRESH_BINARY, 11, 2)
  └─ Creates clear black-and-white image
  └─ Better than global threshold for varying lighting

STEP 6: Dilation & Erosion (optional)
  └─ Improve character connectivity
  └─ cv2.morphologyEx(image, cv2.MORPH_CLOSE, kernel)

STEP 7: Save Preprocessed Image
  └─ cv2.imwrite(output_path, preprocessed_image)

STEP 8: Run Tesseract
  └─ pytesseract.image_to_string(preprocessed_image, lang='eng+ara')
  └─ Extract text with confidence
  └─ Try multiple PSMs (3, 6, 11) if first fails
```

PSM (Page Segmentation Mode) Selection:
```
0: Orientation and script detection only
3: Fully automatic page segmentation (DEFAULT)
6: Uniform block of text
11: Sparse text
13: Raw line

Strategy:
1. Try PSM 3 (automatic)
2. If confidence < 40%: Try PSM 6 (uniform text)
3. If still low: Try PSM 11 (sparse text)
4. Return best result
```

Fallback for PDFs:
```
IF file is PDF:
  1. Try text extraction with PyMuPDF
  2. If text available: Use it directly (fast)
  3. If text empty (scanned PDF): Use OCR pipeline
ELSE IF file is image:
  1. Use OpenCV preprocessing + Tesseract
```

Calculation Logic:
```javascript
function updateCLOPerformance(studentId, courseId, cloId, questionScore, maxScore) {
  // 1. Calculate score percentage
  const percentage = (questionScore / maxScore) * 100;

  // 2. Update student CLO performance
  StudentCLOPerformance.updateOne(
    {studentId, courseId, cloId},
    {
      $push: {attempts: {questionId, score: questionScore}},
      $inc: {totalAttempts: 1, totalScore: questionScore},
      lastAttemptAt: new Date()
    },
    {upsert: true}
  );

  // 3. Calculate average
  const doc = StudentCLOPerformance.findOne({studentId, courseId, cloId});
  const avgScore = doc.totalScore / doc.totalAttempts;

  // 4. Determine mastery level
  const masteryLevel =
    avgScore >= 90 ? "expert" :
    avgScore >= 75 ? "proficient" :
    avgScore >= 60 ? "developing" :
    "beginner";

  // 5. Update mastery
  StudentCLOPerformance.updateOne(
    {studentId, courseId, cloId},
    {avgScore, masteryLevel}
  );
}
```
